# Product: 부산한입 (BusanBite)

Source of truth for *what* to build. PM reads this before assigning any task;
frontend/backend/db read it for context but take actual task instructions
from the PM, not by interpreting this doc themselves.

## One-line concept
외국인 관광객이 한글 메뉴판/안내문을 찍으면 AI가 맥락까지 설명해주고, 필요한
말을 한국어 카드로 만들어 보여주는 여행 도우미 앱. 번역이 아니라 "이해하기 +
전달하기"를 한 흐름으로 연결한다.

## Target users
- 1차: 부산 방문 외국인 관광객 (대만/중화권 비중 최고, 이어서 일본)
- 2차(로드맵): 로컬 식당 상인 ("사장님 모드")
- 3차(로드맵): 부산시 (관광 데이터)

## Supported languages (UI + 번역 출력)
영어, 번체 중국어(대만), 간체 중국어, 일본어. 앱 내부 텍스트/UI도 이 언어들로
전환 가능해야 함 (i18n 처음부터 고려).

## Full feature vision (로드맵 — 전부 한번에 만들지 않음, 아래 MVP 참고)
1. **먹기** — 메뉴판 스캔 → 항목별 이름/설명/맵기/알레르기/먹는 법/가격(통화
   변환) → 주문 카드 생성 (화면 뒤집어서 사장님께 보여주는 UI)
2. **읽기** — 아무 안내문/키오스크/정류장 사진 → "이게 뭐고 어떻게 쓰는지" 설명
3. **말하기** — 마이크로 말하거나 자주 쓰는 문장 칩 선택 → 한국어 카드로 변환,
   같은 뒤집기 UI로 상대방에게 보여줌
4. **AI 챗봇** — 화면 우하단 플로팅 버튼, 여행 중 궁금한 걸 자유 질문으로 물어봄
5. **로컬 메뉴 지도** — 스캔된 메뉴가 가게별로 누적 저장되어, 다음 관광객은
   안 찍어도 바로 조회 가능 (핵심 차별점) — **2026-09-18: DB 제거 결정으로
   보류.** DB 없인 이 기능 자체가 성립 안 됨 (저장할 데이터베이스가 없음).
   나중에 트래픽/예산이 생기면 DB 다시 붙이면서 재개.
6. **사장님 모드** — 상인이 메뉴판 사진 1장 → 4개 국어 메뉴 + QR 자동 생성
7. **분석** — 상인용("이번 달 우리 가게 본 외국인 국적 비율"), 부산시용(관광
   데이터 대시보드)

> **팀원 라이브 데모 (2026-09-18)**: 팀원 한 명이 위 1~4번(먹기 강화판 +
> 말하기 + AI 챗봇)을 정적 HTML로 구현한 라이브 데모를 만들었음
> (`claude.ai/artifact/PrTZ9BbUidr8NrPZhZQTem`). 기능 흐름과 브랜드 디자인
> 모두 이 데모를 기준으로 삼기로 함 — 아래 "브랜드 디자인" 섹션 참고. 전체를
> 한번에 만들진 않고, 먹기 탭 강화부터 순서대로 진행 (아래 MVP 섹션).

## MVP (v1) scope — PM이 이걸로 작업 분배 시작
지금 4개 에이전트가 처음 만들 범위는 **①먹기**입니다 (아래 DB 관련 내용은
2026-09-18 결정으로 로드맵으로 이동됨 — "지금 증분" #4 참고):

- 카메라로 메뉴판 촬영 (Expo 카메라)
- AI가 항목별로: 현지어 이름 / 설명 / 맵기 / 알레르기 성분 / 먹는 법 / **가격**
  반환 (가격은 팀원 데모 반영 — 아래 참고)
- 언어: 영어 + 번체 중국어 먼저 (방문객 비중 1위), 이후 간체/일본어 확장
- ~~스캔 결과를 DB에 저장해서, 같은 가게가 다시 스캔되면 캐시된 결과를 바로
  반환~~ — **DB 제거 결정으로 폐기, 매번 새로 스캔** (아래 #4)
- 메뉴 항목 선택 → 한국어 주문 카드 생성, 화면 뒤집기로 보여주기

### 지금 증분 (2026-09-18, owner 지적 3건)
1. **UI 다국어 지원 실제 구현** — 지금까지 "언어: 영어+번체중국어"는 AI
   번역 결과(메뉴 이름/설명)에만 적용됐고, 앱 화면 자체(버튼/라벨/안내문구)는
   한국어/영어가 뒤섞여 있었음. owner 지적: 외국인 타겟인데 UI가 한국어면
   안 됨. **앱 첫 실행 시 언어 선택 온보딩 화면**을 추가하고, 선택한 언어로
   앱 전체 UI 텍스트(버튼/라벨/안내문구/에러메시지)가 표시되도록 함. v1
   지원 언어는 기존 우선순위 그대로 영어 + 번체 중국어 (이후 간체/일본어
   확장은 로드맵 그대로).
   - **예외**: 주문 카드 뒷면의 한국어 문장("김치찌개 1개 주세요")은 UI 언어
     설정과 무관하게 **항상 한국어 고정** — 이건 한국인 사장님께 보여주는
     용도라 UI 언어를 따라가면 안 됨. 헷갈리지 않게 명확히 구분.
2. **가게 이름은 사용자 입력이 아니라 AI가 판단** — owner 지적: "왜 유저가
   가게 이름을 입력하게 하냐, 네(AI)가 판단해야지". 메뉴판 사진에 상호/
   간판이 보이면 AI가 스캔하면서 같이 추출하도록 변경, 사용자 입력 필드는
   제거. 사진에서 가게 이름을 못 읽으면 null 반환 — 이 경우 "로컬 메뉴 지도"
   재사용(캐시) 매칭은 그냥 스킵하고 새로 스캔 (GPS 기반 매칭 등은 로드맵).
3. **재촬영(뒤로가기) 기능** — 사진을 고른 뒤 마음에 안 들면 다시 찍을 수
   있는 명시적인 방법이 스캔 화면에 있어야 함 (지금은 다시 촬영/갤러리
   버튼을 또 눌러야만 바뀜, 명확한 "취소/재촬영" 동작이 없음).
4. **DB 완전 제거 (배포 비용 이유)** — Railway 최저 티어도 월 $5고, 무료
   MySQL/Redis 대안들은 신뢰성이 낮거나 없어짐(PlanetScale 무료 티어 종료
   등). owner가 무료 배포를 우선하기로 결정 — 백엔드를 완전 무상태로 바꿈
   (`docs/ARCHITECTURE.md`의 "No DB" 섹션 참고). 결과: "로컬 메뉴 지도"
   기능은 로드맵으로 후퇴, 매 스캔마다 OpenAI를 새로 호출(캐시 없음).
- 로그인/회원가입 없음 (v1은 완전 비회원, 마찰 최소화)

**v1에서 제외** (로드맵으로 남김, 나중 단계): 읽기(안내문 스캔), 말하기(상황별
카드), AI 챗봇, 사장님 모드, 분석 대시보드, 간체중국어/일본어.

### 지금 증분 (2026-09-18, 팀원 데모 반영) — 먹기 탭 강화
전체를 한 번에 만들지 않고 이것부터: 팀원 데모의 "먹기" 탭 수준으로 기존 스캔
결과/주문카드 화면을 끌어올림.
- **가격 + 통화 변환**: AI가 원화 가격도 함께 반환, 화면에서 KRW/TWD/JPY/
  CNY/USD 칩으로 전환 가능 (통화 변환은 프론트에서 고정 환율표로 계산 —
  백엔드 API 불필요, 데모의 `RATES` 테이블 방식 그대로)

  여부를 보여주는 "자세히 보기" 토글 섹션으로 교체 — 여전히 AI 추정이라는
  점은 명시
- 먹는 법(howToEat)은 이미 있음, 그대로 유지

**로드맵으로 이동 (지금 안 만듦, 나중에 팀원 데모를 스펙으로 다시 옴)**: 말하기
탭(마이크+문장칩+카드), AI 챗봇(플로팅 버튼+채팅 패널). 만들 때 데모의
인터랙션을 그대로 참고.

## AI layer (새로 추가되는 스택 — docs/ARCHITECTURE.md에도 반영)
메뉴판 사진 → 항목 추출 + 설명 + 번역을 **OpenAI API (GPT-4o 이상, vision 지원
모델)** 로 백엔드에서 처리. 별도 OCR 모듈 없이 한 번의 멀티모달 호출로 처리하는
것을 기본으로 한다. (실제 스캔해보고 정확도 문제가 보이면 그때 전용 OCR 도입
검토 — 그 경우 이 문서와 ARCHITECTURE.md에 기록 후 진행. v1은 자체 OCR을
만들지 않음.)

## Data model implications (db 에이전트 참고, 상세는 db가 docs/DB_SCHEMA.md에 설계)
- 가게(Restaurant) — 스캔 결과를 누적 저장하려면 가게를 식별할 키가 필요
  (v1 제안: 사용자가 가게 이름을 간단 입력, 또는 GPS 좌표 근접 매칭 — PM이
  db/backend와 협의해서 확정)
- 메뉴 항목(MenuItem) — 가게에 속함, 번역/설명/맵기/알레르기 포함
- 이 구조는 관계형 조회(가게별 메뉴 목록, 국가별 집계 등)가 필요해서, v1부터
  **MySQL을 주 저장소로, Redis는 캐시/세션용으로 병행** 사용을 제안합니다.
  (기존 ARCHITECTURE.md는 "Redis 기본, MySQL은 필요시"였는데, 이 제품은 처음부터
  관계형 데이터가 핵심이라 이 부분 변경 필요 — 아래 확인 질문 참고)

## 브랜드 디자인 (2026-09-18 결정)
팀원 데모의 팔레트/타이포를 우리 M3 테마의 브랜드 정체성으로 채택. 제네릭
M3 기본(보라색)에서 이 팔레트로 교체 — M3 컬러 롤 체계는 그대로 유지하고
시드 컬러만 브랜드에 맞게 바꾸는 것. 정확한 M3 매핑은
`docs/ARCHITECTURE.md`의 "Material Design 3 rules" 섹션 참고 (frontend가
구현 기준으로 삼는 곳).

## Differentiation (한 줄)
"한국어를 번역해주는 앱"이 아니라 "한국어를 몰라도 부산 로컬을 경험하게
해주는 앱".

## 시장 데이터 근거 (배경자료: `../부산 관광 시장 현황 및 전망 — 관광 앱 기획 배경자료.pdf`)
아래는 위 PDF에서 MVP 우선순위에 직접 영향을 준 수치만 추림 (전체 수치는
원본 PDF 참고, 수치마다 출처/연도가 다르니 슬라이드에 쓸 땐 원본의 출처 표기
그대로 유지):
- **부산은 대만이 1위** (2026 상반기 47.8만 명, +54%), 중국 2위(+90.7%로 가장
  빠르게 성장) — 언어 우선순위(영어+번체 중국어 먼저, 간체/일본어는 다음)가
  데이터와 일치함
- **자갈치·국제시장**이 대만·중국·일본 관광객 모두의 선호 방문지 상위 3곳에
  공통으로 들어가고, 외국인 방문 증가율도 +114%로 상위권 — v1 파일럿 지역으로
  자갈치·국제시장을 우선하는 게 맞음 (docs/PRODUCT.md 로드맵의 "부산시 보급
  사업" 항목과 일치)
- **체류시간은 -7.5% 감소했는데 지출은 오히려 늘어남(카드 소비 +41.7%)** —
  서로 다른 지표(총액 vs 1인당/체류시간)라 혼동하지 않도록 피칭 시 주의
  (아래 Q&A ⑦ 참고). 참고로 지출 데이터는 카드 기준이라 현금 결제는 안 잡힘.

| ⑥ | 서비스 범위 과대 ("기능이 너무 많은데 다 되나요?") | MVP는 핵심 흐름만 (이 문서의 MVP 섹션). 교통·택시·맛집 지도·루트는 로드맵으로 분리 |
| ⑦ | 데이터 해석 ("1인당 줄었다면서 총액은 늘었는데요?") | 총액과 1인당·비중은 다른 지표/다른 출처(연도도 다름). 슬라이드마다 연도·기준·출처 표기. 시장 지출은 카드 기준이라 현금 결제 누락 → 이것 자체가 결제 장벽의 근거로 활용 가능 |

### MVP에 반영: 알레르기 AI-추정 표시 + 확인 카드 (Q&A ②)
